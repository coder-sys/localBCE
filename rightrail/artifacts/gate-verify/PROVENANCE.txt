gate_verify.exe: the gate's Lean decisions for the producer's publish check and the payer's index, fork and release checks

Lean/Lake executable `gate_verify` (root BlindLedger.Gate.VerifyCli), built from the
`lean/` sources whose manifest is recorded in tools/tcb_report.txt.
One exe, mode-byte frames (every certificate counts only under the AUTHORITY-LINK/v1 the frame carries; a checkpoint is stored, published or released only with the verifier's cosignature; `lean/BlindLedger/Gate/VerifyCli.lean` is the byte layout) (the stateless frame is deleted), run once per request or resident as `gate_verify serve`
(loop of `u32 len | mode byte + frame` requests, each answered only from its own bytes as `u32 len | exit-code byte | line`; a malformed
request exits 2 so the caller sees EOF); exit 0 for ACCEPT, INDEX, STORED
and FORK, 1 for REJECT and HOLD, 2 for a malformed frame (stderr `GATE_VERIFY=FRAME`):
- Frames, by mode byte: 0x01 PUBLISH, 0x02 INDEX, 0x03 STORE, 0x05 RELEASE, 0x07 CUSTODY, 0x08 INSTALL, 0x09 CERT-INDEX,
  0x0A LINK, 0x0B LINK-INDEX. STORE and RELEASE carry the authority part (head link, carried link conflict, the links the
  certificate witnesses name, the witnesses, the fence certificate); INSTALL and LINK answer `Cosign.install` and
  `Cosign.installLink` on the payer's stored chain. A 0x04 frame is malformed. The exact byte layout of each is the header
  comment of `lean/BlindLedger/Gate/VerifyCli.lean`; the answer lines are `GATE_VERIFY=ACCEPT`, `REJECT`, `HOLD <first failure>`,
  `INDEX ...`, `STORED`, `FORK <digest>`, `CUSTODY <step>`, `CERT <answer>`, `CERT-INDEX ...`, `LINK <answer>`, `LINK-INDEX ...`.
ML-DSA-87 (FIPS 204 algorithm) verified by Lean code written from the standard
(Gate/MlDsa87.lean), not by AWS-LC; no validation is claimed.

- Size: 5,702,656 bytes
- SHA-256: 836622ed9578d9470060fbfb5cfdf639040b53b9f1be4c2439116334fae18f90
  (artifacts/gate-verify/gate_verify.sha256; app/right_rail_gate_signer.py runs the exe only if it hashes to this)
- Toolchain: leanprover/lean4 v4.36.0, `lake build gate_verify -d <lean dir>`, linked with
  -Wl,--no-insert-timestamp (lakefile.toml).
- Source manifest: the `manifest` line of tools/tcb_report.txt (the one copy), a SHA-256 over the sources this exe and the two
  engine exes are built from: each exe's import closure (lean/tools/semantic_assurance_gate.py `pinned_source_manifest`) plus
  lean/lakefile.toml, lean/lean-toolchain and lean/lake-manifest.json, each file hashed as LF bytes (= its git blob).
  tests/test_tcb_gate.py recomputes it and fails when one of those files changes until tools/tcb_pin.ps1 is rerun; an edit to any
  other lean/ file does not move it.

Re-pin procedure: when this exe's SHA-256 moves, build it in each of two fresh `git archive <commit> lean` stages and byte-match
both with the in-tree build (a reproduced pair). When only the manifest moves (no exe changes), rerun tools/tcb_pin.ps1 and
commit tools/tcb_report.txt (it requires the in-tree build to equal the pins and the report's gate_engine line). When gate_engine moves (no committed binary), byte-match the same two stages, run `tools/tcb_pin.ps1 -Regen` (sets RR_TCB_REGEN=1: records the new hashes), then plain `tools/tcb_pin.ps1` (a check: built == report), and name the new hashes here (tests/test_tcb_gate.py requires it).
