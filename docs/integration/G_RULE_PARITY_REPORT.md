## Assumptions (how localBCE flags are derived from Lean's rows)

- G9 recipient_not_deceased = 0 when a DMF row for the member is dated strictly before the service date (the snapshot's rows, whether or not Lean finds the snapshot usable).
- G1 eligibility_active = 0 when the member has no enrollment span at all; otherwise 1.
- G3 eligibility period = the span covering the service date (for CAP_820, with the paying plan); with no covering span, the member's first span, so G3 fires.
- G5 provider_enrolled = 0 when the payee or rendering party is on the exclusion rows on the service date, or on the provider death rows dated before it.
- G7 is_duplicate = 1 when the line's exact key (flow kind, member, payee, date, procedure, units, cents) is on a released-set row, on an earlier ALLOW line of the same case, or on an earlier line of the same batch in Lean's canonical order.  The unresolved set and near keys are not localBCE inputs.
- An earlier commit releases a line only when every line of its payment is ALLOW and the payment is not being decided again (`redo`); a re-decided payment's own released line is not its own duplicate.
- The gate's own checkpoint of the released and unresolved sets (used when a set read does not chain) is not modelled: localBCE has no checkpoint, so only the rows of the set read count.
- G2, G4, G6, G8 and G10 flags are set to passing values: no Lean rule exists for them yet (Phase 3).
- A dropped snapshot, or one whose rows do not hash to its declared pin, contributes no rows: Lean treats both as missing (Run.lean `snapshot`).
- A line the vector gives no expected result is not compared, and is not counted as released for later commits (its Lean result is unknown here).
